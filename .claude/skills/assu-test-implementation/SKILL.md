# ASSU 테스트 구현

확정된 테스트 설계와 제품 요구사항을 바탕으로 필요한 테스트만 구현한다. 목표는 테스트 수를 늘리는 것이 아니라, 승인된 사용자 규칙의 회귀를 막는 것이다.

## 수행 절차

1. `docs/testing-strategy.md`와 개발자가 승인한 제품 규칙·기대 결과·테스트 범위를 읽는다. 승인 내용이 불분명하면 구현 전에 확인한다.
2. 테스트 대상과 같은 FSD slice에 `*.test.ts` 또는 `*.test.tsx` 파일을 둔다.
3. 가장 작은 충분한 계층을 선택한다. 순수 로직은 단위 테스트, API 훅은 훅 테스트, 사용자 상호작용은 컴포넌트 테스트로 작성한다.
4. 외부 네트워크·네이티브 의존성만 필요한 최소 범위에서 mock한다. 핵심 비즈니스 로직은 mock하지 않는다.
5. 테스트는 describe/it 블록으로 구조화한다.

   **describe 이름**은 계층에 따라 다르게 쓴다.
   - 단위 테스트: 검증하는 규칙 이름 — `describe('필수 약관 동의 조건', ...)`
   - 컴포넌트 테스트: UI 책임 이름 — `describe('TermsStep 다음 버튼 활성화', ...)`
   - 훅 테스트: 훅 동작 이름 — `describe('useSignup 인증 요청 상태', ...)`

   **it**은 하나의 시나리오. 정상·경계·실패를 각각 별도 케이스로 작성한다 — `it('모든 필수 항목에 동의하면 다음 버튼이 활성화된다', ...)`. 경계값 여러 개는 `it.each([...])('…$value…', ({ value }) => …)` 형식의 **it.each**로 테이블화한다.

   **내부 주석**은 단계가 명확히 나뉠 때 `// Given` `// When` `// Then`으로 구분한다. 한 줄이면 `// When & Then`으로 합치고, 단순 한 줄 검증은 주석을 생략한다.

   **beforeEach**는 `jest.clearAllMocks()`나 store 리셋 같은 공통 인프라 초기화에만 사용하고, 테스트별 Given은 각 it 블록 안에 직접 작성한다.

   실제 matcher·query·render 조합은 리포의 Jest 설정, 매처 등록 상태(`@testing-library/react-native/extend-expect` 등), 접근성 역할 구현에 맞춰 결정한다. 이 스킬은 구조만 안내하고 실행되는 코드 예시를 제공하지 않는다. 복붙할 샘플이 아니라 리포에 이미 존재하는 테스트를 참고 기준으로 삼는다.
6. 테스트를 추가하거나 수정한 뒤 `docs/ai-qa/test-dashboard.md`의 해당 기능 행을 갱신한다. 현황판은 테스트 적용 범위를 기록한다. 기능, 우선순위, 계층, 테스트 대상/시나리오, 테스트 파일, 작성자, 날짜를 기록한다. 작성자는 `git config --get user.name` 값을 **변환하지 않고 그대로** 기록한다. 값이 비었거나 AI 식별자(`Codex`, `Claude`, `Cursor` 등)이면 사용자에게 사용할 이름을 확인하며, AI 식별자를 작성자로 기록하지 않는다. 날짜는 작업 당일 `YYYY-MM-DD` 형식을 쓴다.
7. 작성하거나 수정한 테스트 파일의 정확한 경로, 현황판, 구현 시나리오와 제외 범위를 요약한다. 실행이 필요하면 개발자가 직접 실행하거나 별도로 `assu-test-run`을 호출하도록 안내한다.

## 제한 사항

- 승인되지 않은 테스트 범위를 임의로 넓히지 않는다.
- 제품 요구사항이 불명확하면 추측으로 테스트를 추가하지 않고 확인이 필요한 규칙을 보고한다.
- 테스트 명령, typecheck, lint는 자동 실행하지 않는다.
- 테스트를 편하게 하려고 프로덕션 코드를 과도하게 리팩터링하지 않는다.
