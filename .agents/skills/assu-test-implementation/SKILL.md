# ASSU 테스트 구현

확정된 테스트 설계와 제품 요구사항을 바탕으로 필요한 테스트만 구현한다. 목표는 테스트 수를 늘리는 것이 아니라, 승인된 사용자 규칙의 회귀를 막는 것이다.

## 수행 절차

1. `docs/testing-strategy.md`와 개발자가 승인한 제품 규칙·기대 결과·테스트 범위를 읽는다. 승인 내용이 불분명하면 구현 전에 확인한다.
2. 테스트 대상과 같은 FSD slice에 `*.test.ts` 또는 `*.test.tsx` 파일을 둔다.
3. 가장 작은 충분한 계층을 선택한다. 순수 로직은 단위 테스트, API 훅은 훅 테스트, 사용자 상호작용은 컴포넌트 테스트로 작성한다.
4. 외부 네트워크·네이티브 의존성만 필요한 최소 범위에서 mock한다. 핵심 비즈니스 로직은 mock하지 않는다.
5. 테스트 이름은 중요한 사용자 행동 또는 비즈니스 규칙을 설명한다.
6. 테스트를 추가하거나 수정한 뒤 `docs/ai-qa/test-dashboard.md`의 해당 기능 행을 갱신한다. 현황판은 테스트 적용 범위를 기록한다. 기능, 우선순위, 계층, 테스트 대상/시나리오, 테스트 파일, 작성자, 날짜를 기록한다. 작성자는 현재 저장소의 `git config --get user.name` 값을 GitHub 사용자명으로 기록한다. 값이 없거나 GitHub 사용자명이 불분명하면 사용자에게 확인하며, `Codex`를 작성자로 기록하지 않는다. 날짜는 작업 당일 `YYYY-MM-DD` 형식을 쓴다.
7. 작성하거나 수정한 테스트 파일만 `docs/testing-strategy.md`의 실행 기준에 따라 Jest로 실행한다. 한 작업에서 최초 실행을 포함해 최대 3회 실행한다.
8. 실패 원인을 구분해 처리한다.
   - 대상 테스트 코드·fixture·mock·기능 전용 setup·명령이 승인된 기대 동작을 잘못 표현한 경우, 기대 동작은 유지하고 해당 테스트 측 문제만 수정해 재실행한다. 공용 Jest 설정·전역 setup·의존성 파일 변경은 개발자 승인 없이 하지 않는다.
   - 테스트가 승인된 기대 동작을 올바르게 표현했지만 제품 동작이 다른 경우, 원인·수정 제안·대상 파일을 개발자에게 제시하고 대기한다. 개발자가 수정 범위를 승인한 뒤에는 승인된 범위만 수정하고 Jest를 재실행한다.
   - 정책이 불명확하거나 환경 문제로 결과를 판단할 수 없으면 임의 수정하지 않고, 로그와 개발자 판단이 필요한 내용을 보고한다.
9. Jest 실행이 성공한 경우에만 `docs/ai-qa/test-run-log.md`에 실행 결과와 변경 내역을 기록한다. 실패하거나 중단한 실행은 누적 기록에 남기지 않는다.
10. 작성하거나 수정한 테스트 파일의 정확한 경로, 현황판, 성공 실행 기록, 실행 명령, 시도 횟수, 최종 결과, 승인 후 제품 코드를 수정했다면 그 범위, 구현 시나리오와 제외 범위를 요약해 개발자가 테스트의 적합성을 최종 검토할 수 있게 한다.

## 제한 사항

- 승인되지 않은 테스트 범위를 임의로 넓히지 않는다.
- 제품 요구사항이 불명확하면 추측으로 테스트를 추가하지 않고 확인이 필요한 규칙을 보고한다.
- 전체 테스트, coverage, watch 실행은 별도 요청이나 승인 없이 실행하지 않는다.
- 제품 코드는 개발자가 구체적인 수정 범위를 승인한 뒤에만 변경한다.
- typecheck와 lint는 자동 실행하지 않는다.
- 테스트를 편하게 하려고 프로덕션 코드를 과도하게 리팩터링하지 않는다.
