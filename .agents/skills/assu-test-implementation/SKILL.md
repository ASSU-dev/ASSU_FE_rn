# ASSU 테스트 구현

확정된 테스트 설계와 제품 요구사항을 바탕으로 필요한 테스트만 구현한다. 목표는 테스트 수를 늘리는 것이 아니라, 승인된 사용자 규칙의 회귀를 막는 것이다.

## 수행 절차

1. `docs/testing-strategy.md`와 사용자가 승인한 테스트 범위 또는 설계 문서를 읽는다.
2. 테스트 대상과 같은 FSD slice에 `*.test.ts` 또는 `*.test.tsx` 파일을 둔다.
3. 가장 작은 충분한 계층을 선택한다. 순수 로직은 단위 테스트, API 훅은 훅 테스트, 사용자 상호작용은 컴포넌트 테스트로 작성한다.
4. 외부 네트워크·네이티브 의존성만 필요한 최소 범위에서 mock한다. 핵심 비즈니스 로직은 mock하지 않는다.
5. 테스트 이름은 중요한 사용자 행동 또는 비즈니스 규칙을 설명한다.
6. 테스트를 추가하거나 수정한 뒤 `docs/ai-qa/test-dashboard.md`의 해당 기능 행을 갱신한다. 현황판은 회원가입 등 특정 기능 전용이 아니라 프로젝트 전체 기능의 테스트 이력을 누적한다. 기능, 우선순위, 계층, 테스트 대상/시나리오, 테스트 파일, 작성자, 날짜를 기록한다. 작성자는 현재 저장소의 `git config --get user.name` 값을 GitHub 사용자명으로 기록한다. 값이 없거나 GitHub 사용자명이 불분명하면 사용자에게 확인하며, `Codex`를 작성자로 기록하지 않는다. 날짜는 작업 당일 `YYYY-MM-DD` 형식을 쓴다.
7. 작성하거나 수정한 테스트 파일의 정확한 경로, 갱신한 현황판, 구현한 시나리오와 의도적으로 제외한 범위를 요약하고, 사용자가 실행할 테스트 명령을 안내한다.

## 제한 사항

- 승인되지 않은 테스트 범위를 임의로 넓히지 않는다.
- 제품 요구사항이 불명확하면 추측으로 테스트를 추가하지 않고 확인이 필요한 규칙을 보고한다.
- 테스트 명령, typecheck, lint는 자동 실행하지 않는다.
- 테스트를 편하게 하려고 프로덕션 코드를 과도하게 리팩터링하지 않는다.
