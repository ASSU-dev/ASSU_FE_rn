# ASSU 테스트 작성

사용자가 기능 또는 PR에 테스트 코드 작성을 요청하면, 테스트 설계와 구현을 하나의 흐름으로 연결한다. 사용자는 대상만 짧게 지정하면 되며, 코드에서 알 수 없는 제품 규칙만 추가로 확인한다.

## 입력 처리

- 기능명, 파일 경로, PR 또는 변경 설명 중 하나가 있으면 범위로 사용한다.
- 변경 diff가 있으면 함께 읽는다. 기존 기능이면 관련 소스와 기존 테스트를 읽는다.
- 화면에 보이는 조건, 정책, 예외 처리처럼 코드만으로 확정할 수 없는 규칙은 사용자가 제공한 내용만 사용한다. 핵심 규칙이 불명확하면 구현 전에 짧게 확인한다.
- 회원가입처럼 여러 단계·API·화면을 포함하는 큰 기능이면 전체를 한 번에 구현하지 않는다. 하위 흐름을 위험도 순으로 제안하고, 첫 번째 구현 범위는 하나의 사용자 규칙 또는 하나의 단계로 제한한다.

## 작업 흐름

1. `assu-test-design`의 책임별 계층 판단 기준에 따라 모든 의미 있는 영향 후보와 정상·경계·실패 시나리오를 설계한다. 순수 로직·API 훅·UI 컴포넌트·핵심 사용자 흐름을 모두 검토한다. E2E 후보를 제외한 구현 가능한 단위·훅·컴포넌트 후보는 우선순위와 관계없이 하나의 파일 배치 트리에 함께 제시한다.
2. 사용자 영향, 비즈니스 규칙 영향, 변경 직접성을 기준으로 우선순위를 정한다.
3. 후보 목록을 보여준 뒤, 빠진 사용자 흐름·실패 상황·역할별 예외·팀 정책이 있는지 짧게 확인받고 답변을 설계에 반영한다.
4. 요청 범위가 큰 기능이면 보완된 전체 후보 목록에서 우선순위가 높은 첫 하위 흐름과 그 근거를 제안하고, 사용자가 선택하거나 범위를 승인한 뒤에 그 범위만 구현한다.
5. 요구사항이 충분히 명확하고 사용자가 "작성" 또는 "추가"를 요청한 경우, 승인 후보만 `assu-test-implementation` 기준에 따라 구현한다.
6. 설계만 요청한 경우에는 구현하지 않고 테스트 매트릭스만 제공한다.
7. 구현 후에는 `docs/ai-qa/test-dashboard.md`에 작성자, 날짜, 기능, 테스트 계층, 시나리오, 테스트 파일을 기록하거나 갱신한다. 작성자는 현재 저장소의 `git config --get user.name` 값을 GitHub 사용자명으로 기록한다. 값이 없거나 GitHub 사용자명이 불분명하면 사용자에게 확인하며, `Codex`를 작성자로 기록하지 않는다.
8. 작성한 테스트, 갱신한 현황판, 제외한 범위, 사용자가 실행할 명령을 짧게 보고한다.

## 제한 사항

- 정적 분석과 import 관계는 영향 후보를 찾는 보조 신호일 뿐, 사용자 영향을 증명하지 않는다.
- 테스트 범위를 화면 전체나 관련 파일 전체로 자동 확장하지 않는다.
- 테스트 실행, typecheck, lint는 자동 실행하지 않는다.
