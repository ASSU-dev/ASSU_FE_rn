# ASSU 테스트 작성

사용자가 기능 또는 PR에 테스트 코드 작성을 요청하면, 테스트 설계와 구현을 하나의 흐름으로 연결한다. 개발자가 제품 규칙·테스트 기준·범위를 먼저 확인하고 승인한 뒤 AI가 해당 범위의 시나리오를 설계하고 테스트를 작성한다. 요청에 승인할 정책이나 범위가 빠져 있으면 테스트 설계·작성 전에 확인한다. 코드에서 알 수 없는 제품 규칙은 추측하지 않는다.

## 입력 처리

- 기능명, 파일 경로, PR 또는 변경 설명 중 하나가 있으면 범위로 사용한다.
- 변경 diff가 있으면 함께 읽는다. 기존 기능이면 관련 소스와 기존 테스트를 읽는다.
- 화면에 보이는 조건, 정책, 예외 처리처럼 코드만으로 확정할 수 없는 규칙은 사용자가 제공한 내용만 사용한다. 핵심 규칙이 불명확하면 구현 전에 짧게 확인한다.
- 회원가입처럼 여러 단계·API·화면을 포함하는 큰 기능이면 전체를 한 번에 구현하지 않는다. 하위 흐름을 위험도 순으로 제안하고, 첫 번째 구현 범위는 하나의 사용자 규칙 또는 하나의 단계로 제한한다.

## 작업 흐름

1. 변경 diff, 요구사항, 영향받은 소스, 기존 테스트를 읽는다. 승인된 제품 규칙·테스트 기준·범위가 불명확하면 테스트 설계나 구현을 시작하기 전에 개발자에게 확인한다.
2. 승인된 범위 안에서 `assu-test-design`의 책임별 계층 판단 기준을 사용해 정상·경계·실패 시나리오와 필요한 테스트 파일을 설계한다. 이 범위 안의 시나리오마다 추가 승인을 요구하지 않는다. 새로운 정책이나 승인 범위 확장이 필요하면 멈추고 확인한다.
3. 큰 기능은 승인된 범위를 임의로 넓히지 않는다. 하위 흐름을 정해야 한다면 우선순위와 제안을 보여주고 개발자가 범위를 승인할 때까지 구현을 시작하지 않는다.
4. 설계만 요청한 경우에는 구현하지 않고 매트릭스만 제공한다. 테스트 작성 요청이면 승인된 범위만 `assu-test-implementation` 기준에 따라 작성한다.
5. 구현된 테스트를 대상으로 Jest를 실행하고 실패 로그를 분석한다. 테스트 구현 문제는 기대 동작을 바꾸지 않는 범위에서 수정·재실행한다.
6. 제품 코드 결함으로 판단되면 원인·수정 제안·대상 파일을 개발자에게 제시한다. 구체적인 수정 범위를 승인받은 뒤에만 해당 제품 코드를 수정하고 재실행한다. 정책 불명확·환경 문제·실행 한도 초과 시 중단하고 보고한다.
7. 테스트를 추가하거나 수정하면 `docs/ai-qa/test-dashboard.md`에 작성자, 날짜, 기능, 테스트 계층, 시나리오, 테스트 파일을 기록하거나 갱신한다. 작성자는 현재 저장소의 `git config --get user.name` 값을 GitHub 사용자명으로 기록한다. 값이 없거나 GitHub 사용자명이 불분명하면 사용자에게 확인하며, `Codex`를 작성자로 기록하지 않는다.
8. 대상 테스트가 성공한 경우에만 `docs/ai-qa/test-run-log.md`에 명령, 시도 내역, 최종 결과와 변경 내역을 기록한다.
9. 작성한 테스트, 갱신한 현황판, 성공 실행 기록, 실행 명령과 시도 횟수, 최종 결과, 승인 후 변경한 제품 코드, 제외한 범위를 보고해 개발자가 테스트의 실제 기능 검증 여부를 최종 검토할 수 있게 한다.

## 제한 사항

- 정적 분석과 import 관계는 영향 후보를 찾는 보조 신호일 뿐, 사용자 영향을 증명하지 않는다.
- 테스트 범위를 화면 전체나 관련 파일 전체로 자동 확장하지 않는다.
- 승인된 범위의 대상 Jest 테스트는 `assu-test-implementation` 단계에서 실행한다. 전체 테스트, coverage, watch는 별도 요청이나 승인 없이 실행하지 않는다.
- 제품 코드는 개발자가 구체적인 수정 범위를 승인한 뒤에만 변경한다.
- typecheck와 lint는 자동 실행하지 않는다.
