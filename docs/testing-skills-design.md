# 테스트 스킬 설계

## 결정

아직 `assu-test-design`, `assu-test-implementation` 스킬 파일은 만들지 않았다. 이 문서는 두 스킬을 실제 `.agents/skills`에 추가하기 전의 설계 기준이다.

두 스킬은 역할을 분리한다.

```text
기능 또는 변경 요청
        ↓
assu-test-design
        ↓
테스트 매트릭스와 승인된 범위
        ↓
assu-test-implementation
        ↓
테스트 코드와 실행 안내
```

`assu-test-design`은 코드를 수정하지 않는다. `assu-test-implementation`은 설계된 범위를 넘겨 테스트 대상을 확대하지 않는다.

## 공통 구조

두 스킬은 저장소 안에서 함께 버전 관리한다.

```text
.agents/skills/
├── assu-test-design/
│   └── SKILL.md
└── assu-test-implementation/
    └── SKILL.md
```

초기 버전은 `SKILL.md`만 둔다. 반복적으로 같은 표 형식이나 mock 구성이 필요해질 때만 `references/` 또는 `scripts/`를 추가한다.

공통 제약은 다음과 같다.

- 테스트 파일은 대상 파일과 같은 FSD slice에 둔다.
- 테스트는 사용자에게 관찰되는 결과와 비즈니스 규칙을 우선 검증한다.
- 외부 네트워크와 네이티브 의존성은 필요한 최소 범위에서 mock한다.
- 기존 프로젝트 설정을 존중하며, 현재 API 경계 mock에는 `axios-mock-adapter`를 사용할 수 있다.
- 프로젝트 규칙에 따라 테스트 실행 명령을 자동으로 실행하지 않는다.

## 스킬 1: `assu-test-design`

### 목적

기능 또는 변경 사항을 요구사항과 위험 기준으로 분석해, 구현 가능한 최소 테스트 범위를 설계한다. 현재 구현을 그대로 재현하는 테스트가 아니라 사용자 행동과 비즈니스 규칙을 기준으로 테스트 대상을 정한다.

### 발동 조건

다음과 같은 요청에 사용한다.

- “회원가입 테스트를 설계해줘”
- “이 PR에서 무엇을 테스트해야 해?”
- “지도 검색의 테스트 범위를 정리해줘”
- “정상·경계·실패 케이스를 뽑아줘”

테스트 코드를 바로 작성하거나 이미 승인된 테스트 목록을 구현하는 요청에는 사용하지 않는다.

### 입력

- 대상 기능, 변경 파일 또는 PR 범위
- 기능 요구사항 또는 사용자가 기대하는 동작
- 선택 사항: 이미 존재하는 테스트, 제외할 범위, 우선순위 제약

### 수행 흐름

1. 대상 코드와 관련 요구사항을 읽고, 사용자·비즈니스에 영향을 주는 동작을 식별한다.
2. 동작을 순수 로직, API 훅, UI 컴포넌트, E2E 후보로 분류한다.
3. 각 동작에 대해 정상·경계·실패 사례를 작성한다.
4. 비즈니스 영향, 변경 가능성, 실패 비용을 종합해 우선순위를 정한다.
5. 이미 다른 계층에서 충분히 검증되는 동작과 테스트하지 않을 대상을 제외한다.
6. 필요한 provider, mock 경계, 테스트 데이터만 명시한다.

### 산출물 형식

아래 표를 기본 형식으로 사용한다.

| 우선순위 | 대상 | 계층 | 검증할 행동 또는 규칙 | 정상·경계·실패 | mock·준비물 | 제외 이유 |
| --- | --- | --- | --- | --- | --- | --- |
| 높음 | `validation.ts` | 단위 | 인증 유효 시간 내 다음 단계 진행 | 정상, 만료, 코드 미발송 | 없음 | - |

표 뒤에는 다음 두 항목만 덧붙인다.

- 이번 구현 범위: 우선순위가 높은 항목 중 실제로 작성할 테스트
- 보류 범위: E2E 후보 또는 요구사항이 불명확해 구현하지 않을 항목

### 완료 조건

- 테스트 대상과 제외 대상이 구분되어 있다.
- 각 테스트가 어느 계층에서 검증되는지 명확하다.
- 구현 스킬이 추가 분석 없이 범위를 받아 코드를 작성할 수 있다.

### 중단 조건

요구사항, 성공 기준 또는 사용자 흐름이 불명확해 테스트 기대 결과를 안전하게 정할 수 없으면, 추측으로 테스트를 설계하지 않고 필요한 한 가지를 질문한다.

## 스킬 2: `assu-test-implementation`

### 목적

승인된 테스트 설계 또는 사용자가 명시한 범위 안에서 유지보수 가능한 Jest·React Native Testing Library 테스트를 작성한다.

### 발동 조건

다음과 같은 요청에 사용한다.

- “회원가입 validation 테스트를 구현해줘”
- “이 테스트 매트릭스의 높음 항목을 작성해줘”
- “이 API 훅의 성공과 실패 상태 테스트를 추가해줘”
- “로그인 폼 버튼 활성화 컴포넌트 테스트를 작성해줘”

무엇을 테스트할지 먼저 판단해야 하는 요청에는 설계 스킬을 먼저 사용한다.

### 입력

- `assu-test-design`이 만든 테스트 매트릭스 또는 사용자가 지정한 테스트 대상
- 대상 파일과 기대 동작
- 선택 사항: mock 정책, 제외 항목, 테스트 파일 위치

### 수행 흐름

1. 설계 범위와 대상 코드를 읽고 테스트 파일 위치를 결정한다.
2. 순수 로직은 직접 호출하는 단위 테스트로 작성한다.
3. API 훅은 API 경계를 mock하고, loading·success·error·활성화 조건처럼 사용자 동작에 영향을 주는 상태를 검증한다.
4. UI는 내부 구현이 아니라 입력, 탭, 표시되는 상태, 이동 같은 사용자 결과를 검증한다.
5. API 응답 변환은 mapper 단위 테스트로 분리하며, API 훅에서 중복 검증하지 않는다.
6. 필요한 mock은 해당 테스트 파일 가까이에 최소 범위로 둔다. 공통 mock이 반복될 때만 공용화한다.
7. 수정 파일, 다룬 사례, 제외 사례, 사용자가 실행할 테스트 명령을 보고한다.

### 테스트 계층별 기준

| 계층 | 작성 기준 | 피할 것 |
| --- | --- | --- |
| 순수 로직 | 입력과 반환값, 경계 조건, 오류 규칙 | UI 렌더링이나 네트워크 mock |
| API 훅 | 상태 변화, 캐싱·활성화·재요청의 사용자 영향 | query key 배열 자체 같은 내부 표현 검증 |
| UI 컴포넌트 | 화면 텍스트, 버튼 상태, 사용자 상호작용 | state setter 호출 횟수, 컴포넌트 트리 구조 |
| E2E | 로그인·회원가입·지도 검색·리뷰 작성의 핵심 경로 | 모든 화면의 반복적인 E2E |

### 완료 조건

- 테스트 파일이 해당 FSD slice에 배치되어 있다.
- 설계에서 승인한 사례만 구현했다.
- 정상·경계·실패 중 다룬 범위와 제외한 범위를 보고했다.
- 자동 실행 없이 사용자가 실행할 명령을 안내했다.

### 중단 조건

설계에 없는 동작을 테스트해야 하거나 기대 결과가 불분명하면, 임의로 범위를 넓히지 않는다. `assu-test-design`으로 돌아가거나 사용자에게 확인한다.

## 사용 예시

```text
$assu-test-design 회원가입 단계 이동의 테스트 범위를 설계해줘.

$assu-test-implementation 방금 만든 설계에서 높음 우선순위 항목만 구현해줘.
```

## 초기 작성 순서

1. `assu-test-design/SKILL.md`를 먼저 만들고, 회원가입 테스트 설계에 한 번 적용한다.
2. 설계 결과를 바탕으로 `assu-test-implementation/SKILL.md`를 만들고, `validation.ts`처럼 순수 로직 하나에 적용한다.
3. 실제 사용 중 불필요하거나 빠진 지침만 좁게 수정한다.
4. API 훅과 UI 테스트에서 반복되는 mock 또는 표 형식이 확인되면 그때만 reference를 추가한다.
