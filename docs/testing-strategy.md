# 테스트 전략

## 목적

핵심 사용자 흐름의 회귀를 빠르게 발견하면서, 테스트 작성과 유지보수 비용을 관리한다. 테스트는 구현 세부 사항보다 사용자가 경험하는 결과와 비즈니스 규칙을 검증한다.

## 현재 기반

프로젝트에는 다음 테스트 환경이 구성되어 있다.

- Jest와 `jest-expo`
- `@testing-library/react-native`
- React Query Provider를 포함하는 `renderWithProviders`
- `axios-mock-adapter`

테스트 파일은 대상 파일과 같은 폴더에 `*.test.ts` 또는 `*.test.tsx`로 둔다.

## 기본 원칙

- 사용자 행동과 비즈니스 규칙을 기준으로 테스트한다.
- 사용자에게 관찰되는 결과와 비즈니스 규칙을 우선적으로 검증한다.
- 정상·경계·실패를 기준으로 사례를 설계한다.
- 같은 동작을 여러 테스트 계층에서 중복 검증하지 않는다.
- 테스트 코드의 유지보수 비용도 구현 범위를 결정하는 기준으로 삼는다.

## 테스트 계층

| 대상             | 테스트 방식               | 우선순위     | 예시                                            |
| ---------------- | ------------------------- | ------------ | ----------------------------------------------- |
| 순수 로직        | 단위 테스트               | 높음         | validation, Zod schema, mapper, payload adapter |
| API 훅           | 훅 테스트와 API 경계 mock | 높음         | 요청 성공, 실패, 로딩, 활성화 조건              |
| UI 컴포넌트      | 컴포넌트 테스트           | 중간         | 입력, 버튼 활성화, 오류·성공 UI                 |
| 핵심 사용자 흐름 | E2E 테스트                | 도입 후 검토 | 로그인, 회원가입, 지도 검색, 리뷰 작성          |

각 계층은 자신이 가진 책임만 검증한다. 예를 들어 API 응답 mapper는 순수 함수 단위 테스트로 검증하고, API 훅에서는 loading·success·error 같은 React Query 상태 변화를 검증한다.

### 계층 판단 기준

기능 이름으로 계층을 고정하지 않고, 검증하려는 책임으로 계층을 선택한다. 같은 도메인 규칙도 범위에 따라 여러 계층의 후보가 될 수 있다.

| 검증하려는 책임 | 적절한 계층 | 예시 |
| --- | --- | --- |
| 외부 의존성 없이 입력과 결과만으로 확인 가능한 규칙 | 단위 테스트 | 필수 약관 동의 조건, schema, payload 변환 |
| API·타이머·폼 상태 등 상태 변화와 의존성 연결 | 훅 테스트 | 인증 발송·검증 성공 또는 실패 후 상태 변화 |
| 사용자 입력·탭 후 화면에 보이는 상태 변화 | 컴포넌트 테스트 | 조건부 입력칸, 버튼 활성화, 오류 메시지 |
| 여러 계층을 연결한 사용자 여정 | E2E 후보 | 역할 선택부터 가입 완료까지 |

단계 순서는 순수 로직으로 결정될 때만 단위 테스트다. 실제 버튼 클릭, 화면 전환, API 응답까지 포함하면 컴포넌트 테스트 또는 E2E 후보로 분류한다. 약관도 동의 규칙은 단위, 체크 UI는 컴포넌트, 가입 완료까지의 여정은 E2E 후보로 나눈다.

단위·컴포넌트 테스트로 기본 회귀 방어선을 만든 뒤, 가장 중요한 사용자 흐름에 한정해 E2E를 도입한다. 모든 화면을 E2E로 만들지 않는다.

## 우선순위

테스트 대상은 비즈니스 영향, 변경 가능성, 실패 비용을 종합적으로 고려하여 우선순위를 정한다.

| 기능           | 비즈니스 영향 | 변경 가능성 | 실패 비용 | 우선순위 |
| -------------- | ------------- | ----------- | --------- | -------- |
| 회원가입 검증  | 높음          | 높음        | 높음      | 높음     |
| 지도 검색 API  | 높음          | 높음        | 중간      | 높음     |
| 단순 UI 텍스트 | 낮음          | 낮음        | 낮음      | 낮음     |

## 테스트 설계 방법

각 대상에 대해 구현 전 아래 세 범주를 먼저 정리한다.

| 범주 | 확인할 내용                                                                          |
| ---- | ------------------------------------------------------------------------------------ |
| 정상 | 사용 가능한 입력이나 성공 응답에서 기대 결과가 나오는지                              |
| 경계 | 빈 값, 제한 시간 만료, 공백 문자열, 선택값 누락 같은 경계 조건을 안전하게 처리하는지 |
| 실패 | API 오류, 권한 거부, 잘못된 입력에서 사용자에게 올바른 상태를 보여 주는지            |

예를 들어 회원가입 단계 검증은 인증번호 발송 여부와 남은 시간, 역할 선택, 필수 동의, 파일 업로드 여부처럼 다음 단계 이동을 차단하거나 허용하는 조건을 검증한다.

## 작성 원칙

- 비즈니스 로직은 입력과 결과가 명확한 단위 테스트부터 작성한다.
- UI 테스트는 내부 state, 함수 호출 횟수, 컴포넌트 구조 대신 사용자가 보는 텍스트·상태·상호작용을 검증한다.
- 외부 네트워크에 의존하지 않도록 API 경계를 mock한다. 현재 프로젝트에서는 `axios-mock-adapter`를 사용한다.
- 테스트 파일도 해당 FSD slice의 일부로 취급한다. FSD 의존성 규칙을 유지하며, 테스트 전용 코드가 상위 레이어를 참조하지 않도록 한다.
- 테스트를 편하게 만들기 위한 과도한 프로덕션 코드 리팩터링은 피한다. 테스트 가능성을 높이는 작은 분리는 기능 요구와 함께 검토한다.
- 테스트 이름은 하나의 중요한 사용자 행동이나 비즈니스 규칙을 명확하게 설명한다.

## 권장 테스트 구성

### 순수 로직

Jest로 함수를 직접 호출한다. 외부 상태나 UI 렌더링 없이 빠르고 안정적으로 실행되어야 한다.

대상 예시:

- `validation.ts`
- `signupStepSchemas.ts`
- `signupPayloadAdapters.ts`
- API 응답 mapper

### API 훅

React Native Testing Library의 훅 테스트와 `renderWithProviders`를 사용한다. API 경계를 mock해 성공·실패 응답을 만들고, 로딩·성공·오류 상태와 캐싱, 활성화 조건, 재요청 등 사용자 동작에 영향을 주는 훅의 동작을 검증한다. 응답 변환은 API 훅이 아니라 mapper의 순수 함수 테스트에서 검증한다.

### UI 컴포넌트

사용자 관점으로 렌더링하고 입력 또는 탭을 수행한다. 폼 입력값에 따라 버튼이 활성화되는지, 오류 메시지와 로딩 상태가 올바른지 확인한다.

## 테스트하지 않는 대상

다음은 중요한 회귀를 막는 데 비해 유지보수 비용이 크므로 기본적으로 테스트하지 않는다.

- 단순 스타일과 레이아웃 구조
- React 및 외부 라이브러리 자체의 동작
- 단순 props 전달만 수행하는 컴포넌트
- 내부 함수 호출 횟수처럼 구현 세부 사항에 해당하는 동작
- 동일한 동작을 여러 계층에서 반복 검증하는 테스트

## Coverage 활용

전체 coverage 비율은 강제 목표가 아니라 참고 지표로 사용한다. 신규 또는 변경된 비즈니스 로직을 우선 테스트 대상으로 삼고, 의미 없는 테스트로 수치를 채우지 않는다.

## 프로젝트 전용 테스트 스킬

테스트 설계와 구현을 분리한 스킬을 저장소의 `.agents/skills`에서 관리한다. 저장소 스킬은 팀이 함께 버전 관리할 수 있으며 Codex가 자동으로 탐색한다. 일반적인 테스트 코드 작성 요청은 `assu-test`가 설계와 구현을 연결한다.

| 스킬                       | 책임                          | 산출물                                         |
| -------------------------- | ----------------------------- | ---------------------------------------------- |
| `assu-test`                | 테스트 요청의 설계·구현 연결  | 테스트 설계, `*.test.ts(x)`, 실행 안내         |
| `assu-test-design`         | 기능 분석 및 테스트 범위 결정 | 테스트 매트릭스, 정상·경계·실패 사례, 우선순위 |
| `assu-test-implementation` | 확정된 범위의 테스트 작성     | `*.test.ts(x)`, 필요한 mock, 실행 안내         |

### 테스트 현황판

`docs/ai-qa/test-dashboard.md`는 회원가입에 한정하지 않고 프로젝트 전체 기능의 테스트 이력을 관리한다. 테스트를 추가하거나 보강할 때마다 기능, 우선순위, 계층, 보호하는 규칙, 테스트 파일, GitHub 사용자명, 날짜를 갱신한다.

### `assu-test-design`이 수행할 일

1. 변경 또는 기능에서 사용자·비즈니스 위험이 큰 동작을 식별한다.
2. 각 동작을 순수 로직, API 훅, UI 컴포넌트, E2E 후보로 분류한다.
3. 정상·경계·실패 사례를 표로 정리한다.
4. 비즈니스 영향, 변경 가능성, 실패 비용을 기준으로 구현 우선순위를 제안한다.
5. 구현에 필요한 mock, provider, 테스트 데이터의 범위를 명시한다.

### `assu-test-implementation`이 수행할 일

1. 설계 문서 또는 사용자가 지정한 범위만 구현한다.
2. 대상과 같은 FSD slice 안에 테스트 파일을 둔다.
3. 실제 API 호출과 네이티브 의존성은 필요한 최소 범위에서 mock하며, mock 도구보다 테스트 경계를 우선한다.
4. `docs/ai-qa/test-dashboard.md`에 해당 기능의 테스트 현황을 갱신한다.
5. 테스트가 다루는 동작과 제외한 범위를 보고한다.
6. 프로젝트 규칙상 테스트 명령을 자동 실행하지 않고, 사용자가 실행할 명령을 안내한다.

## 실행 명령

```bash
yarn test
yarn test:watch
yarn test:coverage
```

특정 파일만 확인할 때는 다음처럼 실행한다.

```bash
yarn test validation.test.ts
```

## 도입 순서

1. 회원가입, 지도 검색, 리뷰처럼 변경이 잦거나 실패 비용이 큰 기능의 순수 로직 테스트를 추가한다.
2. 해당 기능의 API 훅에 성공·실패 상태 테스트를 추가한다.
3. 사용자 입력과 단계 이동처럼 중요한 UI 상호작용을 컴포넌트 테스트로 추가한다.
4. 반복되는 테스트 설계·구현 패턴을 스킬에 반영하고 지속적으로 개선한다.
5. 단위·컴포넌트 테스트로 기본 회귀 방어선을 만든 뒤, 로그인·회원가입·지도 검색·리뷰 작성처럼 중요한 흐름에 한정해 E2E 도구와 실행 환경을 결정한다.
