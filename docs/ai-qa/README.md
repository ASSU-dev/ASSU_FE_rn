# ASSU AI 기반 테스트 작성 가이드

## 목적

이 문서는 ASSU에서 AI를 이용해 테스트 코드를 작성하는 공통 방식을 설명한다.

목표는 AI가 화면 전체의 테스트를 대량 생성하는 것이 아니다. 기능 변경 또는 기존 기능에서 **사용자에게 영향이 큰 규칙을 먼저 찾고**, 개발자가 제품 정책을 짧게 확인한 뒤, 필요한 범위의 회귀 테스트만 작성하는 것이다.

```text
짧은 요청
  → AI가 영향 범위와 테스트 후보를 설계
  → 개발자가 제품 규칙만 확인
  → 승인된 범위의 테스트 작성
  → 개발자가 Jest 실행·현황판·PR 기록
```

## 이 방식이 해결하려는 문제

테스트를 기능 단위로 한 번에 작성하면 다음 문제가 생긴다.

- 회원가입·지도처럼 큰 기능은 테스트 범위가 너무 커진다.
- 화면 구조와 내부 상태를 지나치게 테스트해 리팩터링마다 깨진다.
- 중요한 권한·유효성·데이터 변환 규칙보다 단순 UI 테스트가 많아진다.
- AI가 코드만 보고 제품 정책을 추측해 잘못된 테스트를 추가할 수 있다.

이 워크플로는 이를 피하기 위해 AI의 역할을 **설계 초안과 구현 보조**로 제한한다. 제품 정책의 최종 판단과 테스트 실행은 개발자가 맡는다.

## 전체 흐름

```text
┌──────────────────────────────────────────────┐
│ 개발자                                        │
│ "이 PR 테스트 코드 작성해줘"                  │
└───────────────────────┬──────────────────────┘
                        ▼
┌──────────────────────────────────────────────┐
│ assu-test                                    │
│ 범위 확인 · diff·관련 코드·기존 테스트 읽기   │
└───────────────────────┬──────────────────────┘
                        ▼
┌──────────────────────────────────────────────┐
│ assu-test-design 기준                         │
│ 영향 후보 · 위험도 · 정상/경계/실패 설계      │
└───────────────────────┬──────────────────────┘
                        ▼
┌──────────────────────────────────────────────┐
│ 개발자 확인                                   │
│ 코드로 알 수 없는 제품 정책만 짧게 확정       │
└───────────────────────┬──────────────────────┘
                        ▼
┌──────────────────────────────────────────────┐
│ assu-test-implementation 기준                │
│ 승인 범위의 최소 테스트 코드 작성             │
└───────────────────────┬──────────────────────┘
                        ▼
┌──────────────────────────────────────────────┐
│ 개발자                                        │
│ Jest 실행 · 현황판·결과를 PR에 기록           │
└──────────────────────────────────────────────┘
```

## 스킬 구성

스킬은 저장소의 `.agents/skills/`에 있어 팀원과 함께 버전 관리한다.

### 파일 구조

```text
ASSU_FE_RN/
├── .agents/skills/                         # Codex·Cursor가 읽는 스킬 원본
│   ├── assu-test/SKILL.md                  # 일반 요청의 진입점
│   ├── assu-test-design/SKILL.md           # 무엇을 테스트할지 설계
│   └── assu-test-implementation/SKILL.md   # 승인 범위의 테스트 구현
│
├── .claude/skills/                         # Claude Code 호환 진입점
│   ├── assu-test/SKILL.md
│   ├── assu-test-design/SKILL.md
│   └── assu-test-implementation/SKILL.md
│
├── docs/
│   ├── testing-strategy.md                 # 프로젝트 테스트 정책
│   └── ai-qa/
│       ├── README.md                        # 이 가이드
│       └── test-dashboard.md                # 기능별 테스트 이력
│
└── src/features/<기능>/                    # 실제 테스트 코드 위치
    ├── model/
    │   ├── validation.ts
    │   └── validation.test.ts              # 순수 로직 테스트
    ├── api/
    │   ├── useFeatureQuery.ts
    │   └── useFeatureQuery.test.tsx        # API 훅 테스트
    └── ui/
        ├── FeatureForm.tsx
        └── FeatureForm.test.tsx            # 컴포넌트 테스트
```

테스트 파일은 별도 `tests/` 폴더에 모으지 않고, 검증 대상과 같은 FSD slice에 둔다. 그래서 기능을 수정할 때 관련 테스트를 같은 폴더에서 함께 찾을 수 있다.

테스트 설계 결과는 E2E 후보를 제외한 단위·훅·컴포넌트 후보를 우선순위와 관계없이 하나의 FSD 트리로 함께 보여 준다. 예를 들어 순수 검증 로직을 선택했다면 아래처럼 관련 소스와 새 테스트 파일을 명확히 표시한다.

```text
src/features/<기능>/model/
├── validation.ts             # 관련 소스
└── validation.test.ts        # (새 파일)
```

기존 테스트를 보강하는 경우에는 `(기존 파일)`, 새로 만드는 경우에는 `(새 파일)`로 구분한다.

### 스킬이 이어지는 방식

```text
"회원가입 기능 테스트 코드 작성해줘"
                │
                ▼
        assu-test/SKILL.md
        요청 범위 확인·작업 흐름 선택
                │
       ┌────────┴────────┐
       ▼                 ▼
설계만 요청          코드 작성 요청
       │                 │
       ▼                 ▼
assu-test-design   assu-test-design
테스트 매트릭스     영향·시나리오 설계
작성                      │
                          ▼
                 개발자 정책 확인·범위 승인
                          │
                          ▼
              assu-test-implementation
              같은 FSD slice에 *.test.ts(x) 작성
                          │
                          ▼
                개발자가 yarn test 실행
```

| 스킬 | 파일 | 사용 시점 | 역할 |
| --- | --- | --- | --- |
| `assu-test` | `.agents/skills/assu-test/SKILL.md` | “테스트 코드 작성해줘”처럼 설계가 없는 일반 요청 | 분석·설계·구현 흐름을 연결하는 진입점 |
| `assu-test-design` | `.agents/skills/assu-test-design/SKILL.md` | 무엇을 테스트할지 먼저 검토할 때 | 영향 후보, 우선순위, 테스트 매트릭스 작성 |
| `assu-test-implementation` | `.agents/skills/assu-test-implementation/SKILL.md` | 범위가 이미 승인됐을 때 | 승인된 시나리오의 테스트 코드만 작성 |

### `assu-test`

팀원이 가장 자주 쓰는 진입 스킬이다.

- 기능명, PR, 파일 경로, 변경 설명 중 하나를 범위로 사용한다.
- 변경 PR이면 diff를 읽고, 기존 기능이면 관련 코드와 기존 테스트를 읽는다.
- 기능이 크면 순수 로직·API 훅·UI 컴포넌트·핵심 흐름을 모두 검토해 후보 전체를 위험도 순으로 보여 준다. 실제 구현은 그중 첫 승인 범위만 진행한다.
- E2E 후보를 제외한 구현 가능한 단위·훅·컴포넌트 후보는 하나의 파일 배치 트리로 함께 제시한다.
- 후보를 제시한 뒤, 빠진 사용자 흐름·실패 상황·역할별 예외·팀 정책이 있는지 개발자에게 확인받고 설계에 반영한다.
- 사용자 요청이 “작성”이고 범위·제품 규칙이 명확하면 승인 후보를 구현까지 연결한다.
- 범위가 크거나 제품 정책이 불명확하면 테스트를 대량 작성하지 않고, 첫 후보와 확인 질문을 제안한다.

### `assu-test-design`

테스트 코드 작성 전에 “무엇을 테스트해야 하는가”를 결정한다.

- 정적 import 관계와 변경 파일은 영향 **후보**를 찾는 보조 신호로만 사용한다.
- 사용자 영향, 비즈니스 규칙 영향, 변경 직접성을 함께 본다.
- 정상·경계·실패 상황을 Given / When / Then으로 정리한다.
- 가장 작은 충분한 계층을 선택한다.
- 테스트 대상의 이름이 아니라 검증하려는 책임으로 계층을 정한다. 예를 들어 약관 규칙은 단위, 약관 체크 UI는 컴포넌트, 가입 완료까지의 약관 흐름은 E2E 후보가 된다.
- 단계 순서도 순수 로직이면 단위, 실제 버튼 클릭·화면 전환·API 응답을 포함하면 컴포넌트 또는 E2E 후보로 분류한다.
- 스타일, 레이아웃, 라이브러리 내부 동작, 다른 계층에서 중복된 검증은 제외한다.

출력에는 전체 후보 표와 아래 보충 항목이 포함된다. 첫 구현 후보만 보여 주고 나머지 후보를 생략하지 않는다.

| 우선순위 | 대상 | 영향 근거 | 테스트 계층 | 시나리오 | Mock 필요 여부 | 제외 사유 |
| --- | --- | --- | --- | --- | --- | --- |

- 계층 검토 현황
- 파일 배치 — E2E를 제외한 단위·훅·컴포넌트 후보 전체
- 첫 구현 승인 후보
- 가정 및 검토 사항
- 미포함 범위
- 누락 흐름 확인 요청

### `assu-test-implementation`

설계 또는 개발자 요청으로 범위가 확정된 뒤에만 사용한다.

- 대상과 같은 FSD slice에 `*.test.ts` 또는 `*.test.tsx`를 둔다.
- 순수 로직은 단위 테스트, API 훅은 훅 테스트, 사용자 상호작용은 컴포넌트 테스트로 작성한다.
- 네트워크·네이티브 의존성만 최소 범위로 mock한다.
- 핵심 비즈니스 로직은 mock하지 않는다.
- 승인되지 않은 시나리오를 임의로 추가하지 않는다.
- `docs/ai-qa/test-dashboard.md`에 회원가입·지도 검색·리뷰 등 프로젝트 전체 기능의 테스트 이력을 누적한다.
- 추가·보강한 테스트의 기능, 우선순위, 계층, 보호 규칙, 파일, GitHub 사용자명(`git config --get user.name`), 날짜를 갱신한다.
- 테스트 실행·typecheck·lint는 자동 실행하지 않고, 실행 명령만 안내한다.

## Codex·Cursor·Claude Code 호환성

세 스킬은 `name`, `description`, Markdown 지시문으로 구성된 `SKILL.md` 형식이다. 특정 모델 전용 프롬프트 문법이나 도구 호출을 넣지 않았으므로, Agent Skills를 지원하는 도구에서 같은 내용을 사용할 수 있다.

다만 **파일 형식은 공유되지만 자동 탐색 경로는 도구마다 다르다.**

| 도구 | 현재 스킬 위치 사용 | 팀에서의 사용 방법 |
| --- | --- | --- |
| Codex | 가능 | 이 저장소의 `.agents/skills/`를 프로젝트 스킬로 사용한다. |
| Cursor | 가능 | Cursor는 `.agents/skills/`를 프로젝트 스킬 경로로 자동 탐색한다. |
| Claude Code | 가능 | `.claude/skills/`의 호환 진입 파일이 `.agents/skills/` 원본을 읽는다. |

따라서 `.agents/skills/`를 팀의 단일 기준 원본으로 유지한다. `.claude/skills/`에는 원본 파일을 읽도록 지시하는 작은 호환 진입 파일만 둔다. 스킬 규칙을 변경할 때는 `.agents/skills/`만 수정하면 되며, 내용이 두 벌로 갈라지지 않는다.

도구별 요청 방식은 아래처럼 약간 다를 수 있다.

```text
Codex:  $assu-test 이 PR 테스트 코드 작성해줘.
Cursor: 이 PR 테스트 코드 작성해줘. 또는 스킬 선택 후 요청
Claude Code: /assu-test 이 PR 테스트 코드 작성해줘.
```

어떤 도구를 쓰더라도 핵심 입력과 결과는 같다. 기능 또는 PR 범위를 주면 AI가 테스트 후보를 제안하고, 제품 정책이 불명확할 때만 개발자에게 확인한다.

## AI가 우선순위를 정하는 기준

아래 기준은 회원가입뿐 아니라 지도 검색, 리뷰, 알림, 로그인 등 모든 기능에 공통으로 적용한다.

| 기준 | AI가 확인하는 질문 |
| --- | --- |
| 사용자 영향 | 사용자가 입력·이동·결과에서 다른 경험을 하는가? |
| 비즈니스 규칙 영향 | 권한, 유효성, 데이터 정확성, 저장·삭제 조건처럼 틀리면 비용이 큰가? |
| 변경 직접성 | 이번 변경이 해당 규칙을 직접 바꾸었는가? |

| 기능 | 높은 우선순위가 될 수 있는 규칙 예시 |
| --- | --- |
| 회원가입 | 인증 완료 조건, 필수 동의, 역할별 입력 검증, 가입 요청 payload |
| 지도 검색 | 검색 결과 변환, 좌표 보완, 빈 검색어 요청 차단, 필터 상태 |
| 리뷰 | 작성자 수정·삭제 권한, 수정 후 목록 갱신, 실패 시 기존 내용 유지 |
| 알림 | 읽음 처리 후 미읽음 수 갱신, 다른 사용자의 상태 변경 차단 |
| 로그인 | 성공·실패 처리, 토큰 저장, 역할별 화면 이동, 보호 화면 접근 제어 |

테스트 시나리오는 항상 다음 세 방향을 먼저 검토한다.

| 구분 | 질문 |
| --- | --- |
| 정상 | 조건을 만족했을 때 기대 결과가 나오는가? |
| 경계 | 조건이 막 바뀌는 지점에서도 규칙이 유지되는가? |
| 실패 | 조건을 만족하지 못했을 때 올바르게 막히거나 안내되는가? |

## 팀원이 요청하는 방법

### PR 변경에 테스트를 붙일 때

```text
이 PR 테스트 코드 작성해줘.
```

AI는 변경 diff와 관련 코드를 읽고 이번 변경에 필요한 후보를 제안한다.

### 기존 기능에 테스트를 붙일 때

```text
지도 기능 테스트 코드 작성해줘.
```

AI는 관련 코드와 기존 테스트를 읽고, 현재 테스트 공백과 첫 구현 후보를 제안한다.

### 설계만 필요할 때

```text
리뷰 수정 기능 테스트 설계만 해줘.
```

이 경우 테스트 매트릭스만 만들고 코드는 수정하지 않는다.

### 범위가 이미 정해졌을 때

```text
검색 결과에 좌표가 없을 때 위치를 보완하는 시나리오만 테스트 코드로 작성해줘.
```

이 경우 지정한 규칙 외의 테스트는 추가하지 않는다.

### 스킬을 명시하고 싶을 때

```text
$assu-test 이 PR 테스트 코드 작성해줘.
$assu-test-design 지도 검색 기능의 테스트 공백을 분석해줘.
$assu-test-implementation 승인된 본인인증 조건만 테스트로 작성해줘.
```

## 큰 기능을 요청했을 때

회원가입이나 지도처럼 여러 화면·API·상태가 섞인 기능은 전체를 한 번에 테스트하지 않는다.

```text
개발자: 회원가입 기능에서 테스트 코드 작성해줘.

AI: 기능 범위가 크므로 다음 순서를 제안합니다.
    1. 본인인증 단계 완료 조건
    2. 역할별 입력 검증
    3. 가입 요청 payload 변환
    4. 중복 확인 API 성공·실패 처리
    5. 단계 이동 UI 상호작용

    1번부터 진행할까요?
```

이때 개발자는 전체 설계를 다시 만들 필요 없이 아래 중 하나만 답하면 된다.

```text
1번 진행해줘.
가장 영향이 큰 것부터 작성해줘.
주소가 안 보이면 주소 오류는 없어야 해.
```

첫 두 답변은 구현 범위를 승인하는 말이고, 마지막 답변은 코드로 알 수 없는 제품 정책을 확정하는 말이다.

## AI가 개발자에게 질문하는 경우

AI는 제품 정책을 추측하지 않는다. 아래처럼 코드만 보고 결론 낼 수 없는 경우에만 짧게 확인한다.

```text
AI: 검색 결과에 좌표가 없고 상세 조회에도 좌표가 없으면,
    검색 목록에는 남기고 지도 이동만 막을까요?
    아니면 검색 결과에서도 제외할까요?

개발자: 검색 목록에는 남기되 지도 이동은 오류로 처리해줘.
```

확정된 답변은 테스트 명세가 된다.

```text
- 좌표가 있으면 상세 조회 없이 지도 이동 가능
- 좌표가 없고 상세 조회에 좌표가 있으면 보완 후 이동 가능
- 두 곳 모두 좌표가 없으면 목록에는 남지만 지도 이동은 실패
```

## 적용 사례는 별도 PR로 관리

이 문서는 모든 기능에서 사용하는 공통 워크플로와 스킬 사용법만 다룬다. 특정 기능의 AI 분석 결과, 제품 정책 확인, 테스트 코드, 실행 결과는 해당 기능 PR에서 함께 관리한다.

기능 PR에 남기는 기록은 다음 순서를 권장한다.

```text
기능 변경 또는 기존 기능 범위
→ AI 영향 분석과 테스트 시나리오
→ 개발자 제품 정책 확인
→ 테스트 코드
→ Jest 실행 결과
```

예를 들어 회원가입 주소 규칙이나 지도 검색 위치 보완 규칙은 이 가이드가 아니라, 해당 기능의 테스트 코드와 같은 PR에서 기록한다.

## 테스트 실행

스킬은 테스트를 자동 실행하지 않는다. 테스트 코드를 작성한 뒤 AI가 실행할 명령을 안내하고, 개발자가 터미널에서 실행한 결과를 다시 AI와 공유한다.

```text
AI: 주소 검증 테스트를 추가했습니다.
    아래 명령으로 실행해 주세요.

개발자: yarn test src/features/signup-user-flow/model

개발자: 테스트 실행했어. 결과 확인해줘.
          또는 실패 로그를 그대로 붙여넣기

AI: 통과 결과를 요약하거나, 실패 원인을 분석·수정합니다.
```

가장 확실한 방법은 터미널 출력을 대화에 그대로 붙여넣는 것이다. Codex 안에서 같은 터미널을 사용 중이라면 "방금 테스트 결과 확인해줘"라고 말해도 된다.

### 전체 테스트 실행

```bash
yarn test
```

### 특정 영역만 실행

테스트 파일 또는 폴더를 지정한다.

```bash
yarn test src/features/signup-user-flow/model
yarn test src/features/map-search
```

### 실행 결과에 따른 다음 대화

| 실행 결과 | 개발자가 AI에게 보내는 말 | AI가 하는 일 |
| --- | --- | --- |
| 통과 | `테스트 통과했어. PR 요약 업데이트해줘.` | 통과한 범위와 제외 범위를 PR용으로 요약 |
| 실패 | `테스트 실패했어. 이 로그 원인 봐줘.` | 테스트 코드·공통 설정·프로덕션 코드 중 원인을 구분해 분석 |
| 정책 불일치 | `테스트는 통과하지만 이 동작은 제품 정책과 달라.` | 요구사항을 다시 확인하고 테스트 명세와 구현 범위를 수정 |

## PR에 남길 내용

PR에는 긴 분석 전문 대신 아래 네 가지를 짧게 남긴다.

```markdown
## 테스트

- AI 분석 범위: 본인인증 단계 완료 조건
- 개발자 확인 규칙: 인증번호 발송 후 유효 시간 안에만 다음 단계 진행 가능
- 추가한 테스트: 정상 1건, 경계 1건, 실패 1건
- 테스트 현황판: `docs/ai-qa/test-dashboard.md` 갱신
- 실행: `yarn test src/features/signup-user-flow/model` 통과
```

AI 분석 문서가 필요하면 PR에서 이 README 또는 기능별 기록 문서로 링크한다.

## 운영 원칙

- AI 제안은 초안이며, 제품 정책을 확정하지 않는다.
- 테스트는 가장 작은 충분한 계층에서 작성한다.
- 화면 전체나 관련 파일 전체를 자동으로 테스트 범위에 넣지 않는다.
- 외부 API·네이티브 의존성만 최소 범위로 mock한다.
- 같은 동작을 단위·훅·UI 테스트에서 반복 검증하지 않는다.
- 테스트 실행 결과는 개발자가 확인하고 PR에 남긴다.
- 스킬 규칙을 변경할 때는 `.agents/skills/*/SKILL.md` 변경도 함께 리뷰한다.
